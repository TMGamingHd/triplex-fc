# Review of the flight core by a second reader

> Status: **reference, written 19 Oct 2026**. A source-code inspection of `core/` and `supervisor/` in the manner of NASA-STD-8739.9 section 7.7, done by a reader who had not written the part under reading, with every finding either fixed and pinned by a test and a mutant, or recorded as open. **It is not an independent review and does not replace one**: section 1 says exactly how far its independence goes. Reproduce with section 8.

## 1. What this is, and what it is not

* **Reader.** An AI model (Claude) in a fresh session, with no memory of the sessions that wrote most of this code. The author of the code is, in effect, the same kind of tool working with the project's owner. A fresh session with an adversarial brief finds what a rereading by the author misses (it found eight things here), but it shares the author's blind spots in kind: it can be wrong in the same direction. The owner's own reading is the missing second pair of eyes.
* **Not NASA-STD-8739.9 compliant.** That standard asks for at least three people with the roles author, moderator, reader and recorder, the author present, and measured entry and exit criteria. This was one reader. What was kept from it: the source-code checklist (7.7.1), the defect classification (6.3.6.7: major, minor, clerical, by type), the habit of consuming the static-analysis results before reading, and the rule that a defect is closed only by a change that is verified.
* **What an outside human reader should still do** (section 7): the parts that were not read, the physics of the guidance, and the question the project cannot ask of itself, namely whether the *requirements* are the right ones.

## 2. Method

1. **Entry.** The code builds with warnings as errors, 100 % of its lines are executed by the tests, clang-tidy, cppcheck and `tools/check_standard.py` are clean (`STATUS.md`). A reader does not spend attention on what the tools already check.
2. **Reading.** Safety-critical code first, in the order the claim depends on it: the voter and the CRC, the manager, the actuator node, the ground-command path, the clocks, the supervisor. Each file was read against NASA-STD-8739.9 7.7.1: (a) accuracy and completeness against the requirements; (b) agreement with the design; (c) the coding standard; (d) latent errors: index out of range, buffer overflow, divide by zero, a cast out of range, an uninitialised or unchecked value; (e) traceability to requirements; (f) traceability to design; (g) the analysers' output. The questions asked of every state variable were *what flips it, who checks it, and what does the system do if it is wrong*, and of every input *what if it is missing, repeated, late, early, frozen, out of range*.
3. **Scans.** For the code not read line by line: every float-to-integer cast, every division, every `sqrt`/`acos`/`log`, every array index taken from outside, with the guard looked up for each.
4. **Closing.** A finding is closed when a test that fails without the fix passes with it, **and** a mutant that removes the fix is killed by the suite (`tools/mutation/mutations.py`). Where the test had to be shown to fail, it was run against the original code first.

Eight findings in about 5,500 lines read is one in 700 lines. ## 5. Observations: left as they are, with the reason

| # | Where | Observation | Decision |
|---|---|---|---|
| O-1 | `redundancy.hpp` `sanitize_config` | An all-zero ground key with authentication on is replaced by the **public bench key**, not refused. "Better than zeros" for a bench, but a failed provisioning then silently leaves the command path open to anyone who knows the public key. | Accepted for the bench (`LIMITATIONS.md` 5, REC-13 of the FMECA). **Change before any real uplink:** fail closed (accept no ground command) and say so. The owner's decision. |
| O-2 | `voter.hpp` | A Triplex "agrees" when each channel is within one tolerance of the **median**, so two channels can be two tolerances apart and both be believed; the Duplex test is pairwise within one tolerance. The thresholds of the campaign are stated against the median, so this is the design, but the pairwise spread a Triplex tolerates is twice what the word "tolerance" suggests. | Documented here and in `FAULT_RESPONSE.md`. |
| O-3 | `fault_monitor.hpp`, `act.hpp` | The detectors (`ChannelMonitor`, `AlphaCount`, `StuckDetector`) hold copies of their parameters (the window mask, the leaky constant, the threshold, the stuck limit) outside the integrity check. An upset in one is not seen: for example an `AlphaCount` threshold with its top bit flipped switches the intermittent-fault detector off for that computer on that replica. | **Open, recommended** (REC-09 of the FMECA): the scrub rebuilds each detector's parameters from the checked configuration every frame. Probability low, effect a silent loss of one detector on one replica, which the other replicas and the digest do not see. |
| O-4 | `act_ground.hpp` | ACT's ground-command path has no state sharing: after a reset it has no counter history and accepts the first authentic frame, so a recorded ClearSafe with its ARM could be replayed once after an ACT reset. The computers can restore their counters from their peers' state shares (FDIR-041); ACT has no peers. | Accepted with the bench key (O-1); a real uplink needs ACT to take its counter from the computers' shares. |
| O-5 | `supervisor.hpp` `SupConfig` | Beyond `config_ok()`, the supervisor's configuration is not validated: `resets_before_cycle` above 8 (the size of the history) means it never power-cycles. | Constants in the firmware; noted. |
| O-6 | `protocol.hpp` | SYNC, heartbeat and state-share frames are unauthenticated: a node that sends a wrong frame number or a false heartbeat is believed by the followers. | The bus is trusted by design (`LIMITATIONS.md` 5); the software FMEA lists the data faults that follow (`FMECA.md` section 6, REC-18 and REC-19). |

## 6. What the review found about the checks themselves

The brief was "is the verification working", and the reading was only half of the answer. The other half came from running it.

1. **The weekly mutation workflow had never passed.** Its three scheduled runs (5, 12 and 19 October) all ended at the six-hour limit of a job. The unit-test job was cancelled each time without a verdict; the simulator job ran 5.5 hours and reported 17 "survivors"; together they used about 18 runner-hours a week against a free plan of 2,000 minutes a month. The workflow is now sharded (6 and 8 shards, each well inside four hours), runs monthly and on demand, and the fast pass of the unit mutants re-runs its survivors with the sanitizers (`.github/workflows/mutation.yml`, `run_unit.py --shard --rerun-survivors`).
2. **The 17 survivors were 17 stale patterns, not 17 untested behaviours.** A mutant is a piece of text to find; when the code is refactored the text is gone and the runner reported "not killed". On this branch **22 of the 481** simulator mutants that were in the table were stale: eleven target code that moved or was rewritten (the thrust, the wind, the throttle, the engine cut-off, the mass at separation), eleven match two or three places after the code was duplicated. Each was a behaviour that mutation testing had **silently stopped checking**. All 22 are re-anchored (the duplicates one mutant per copy, so <!--m:mutants_sim-->494<!--/m--> now), and `tools/mutation/check_tables.py` (CI, one second; `sim/tests/test_mutation_tables.py`) fails when a pattern no longer occurs exactly once. One name was defined twice, the second silently overriding the first. And one core mutant (`rs_resync_frames_out_of_schedule`) was stale and would have crashed the unit run.
3. **Seventeen of the <!--m:core_headers-->38<!--/m--> headers of the core and the supervisor had no mutant at all**, among them the safety-relevant `fault_monitor.hpp` (the 3-of-5 window, the leaky count and the stuck detector: the detection logic itself), `auth.hpp`, `act_ground.hpp`, `consensus.hpp`, `crc8.hpp`, `integrity.hpp`, `flightlog.hpp` and `resetlog.hpp`. "Every mutant killed" was true and said nothing about them. Eighty mutants were added for these headers and the ones this review changed; the results are in `STATUS.md` section 3. `check_tables.py --report` lists the headers with none: <!--m:headers_without_mutants-->9<!--/m--> of core and supervisor (the guidance, navigation and attitude control, the sensor driver) and <!--m:sim_headers_without_mutants-->12<!--/m--> of `sim/vehicle` (the mission code, the propulsion model, the surfaces, the CFD tables). They are the parts that carry no mutants, and the table is the proof that this is a stated gap and not an oversight.
4. **The numbers in the documents were not the repository's.** The status page said 801 tests (the suite had 877), 34 decisions (58), "all 31"; the proof page said 691 tests; the coding standard gave the manager's size as 1,080 bytes in one place and 1,432 in another. Every number a current document quotes now comes from `tools/docs/metrics.py` and CI fails when one is stale.

## 7. What an outside human reader should do, in order

1. **`redundancy.hpp`, `act.hpp`, `act_ground.hpp`, `auth.hpp`, `sync_clock.hpp`, `supervisor.hpp`**: the part the claim stands on, about 3,500 lines. Read it against `FAULT_RESPONSE.md`, `SAFE_MODE.md` and `HAZARDS.md` and try to name a sequence of events the campaign did not run.
2. **The requirements, not the code.** Whether the claim in `SAFETY_CASE.md` G0 is the right one, whether the tolerances and persistence constants mean what the physics needs, whether "fail-passive after the second fault" is acceptable for what it models. No tool and no second reader of the same lineage can say.
3. **The guidance** (`peg`, `descent`, `mission`, `nav`): not read here; it has no mutants and has run on the host only.
4. **Attack the bus-level assumptions** of `LIMITATIONS.md` 2: inconsistent omission and a babbler are modelled by nobody.

## 8. Reproduce

```bash
python3 tools/mutation/check_tables.py                   # no mutant has gone stale (a second)
python3 tools/mutation/check_tables.py --report          # which headers have how many mutants
python3 tools/mutation/run_unit.py --fast --rerun-survivors --jobs 8                    # the core mutants (about two hours on 12 threads)
python3 tools/mutation/run_unit.py --fast --changed-since origin/main                   # only the headers a change touched
python3 tools/mutation/run_sim.py --jobs 8                                              # the simulator mutants
cmake -S . -B build -G Ninja -DTFC_SANITIZE=ON && cmake --build build && build/tfc_tests act_an_upset   # a finding's test
```
