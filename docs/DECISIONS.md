# Design decisions (ADR log)

## ADR-001: C++17 subset for flight logic
**Decision:** Portable `core/` in C++17, header-only, no heap, no exceptions, no RTTI, warnings as errors.
**Why:** SpaceX's public Starship software postings ask for C++, Rust or another systems language and real-time embedded experience; public writing about its flight software describes C and C++. A restricted C++ subset is the industry pattern for flight code (MISRA/JSF-style rules). **Alternatives:** C (simpler to certify, less expressive), Rust (attractive, but a weaker toolchain fit for Zephyr today). **Revisit:** Rust for a non-critical tool.

## ADR-002: Zephyr RTOS on the target
**Decision:** Zephyr, with the portable core tested on `native_sim`.
**Why:** Modern, upstream, actively maintained, first-class support for the Nucleo-G474RE (FDCAN, SPI, PWM, watchdogs) and an ISM330DHCX sensor binding, plus real space-industry interest (for example NASA cFS being ported to Zephyr by a space-electronics company). Its `native_sim` target lets the same firmware run on a PC for CI. **Honest note:** SpaceX's own stack is not public and what has been described publicly is dated (Linux and VxWorks have been mentioned). No one will hire on RTOS brand; what transfers is deterministic scheduling, priority discipline, timing measurement and testing. **Alternatives:** FreeRTOS (ubiquitous, lighter), bare metal (max determinism, fewer marketable skills). **Fallback:** if Zephyr bring-up stalls beyond milestone M1 by 2 weeks, drop to FreeRTOS; `core/` is unaffected.

## ADR-003: Time-triggered schedule at 100 Hz
**Why:** Predictable, measurable, easy to reason about for voting, and it mirrors how safety-critical buses are scheduled. **Alternative:** event-driven; simpler but jitter is harder to bound.

## ADR-004: Classic CAN 1 Mbit/s for v1
**Why:** The USB-CAN adapter's FD support with default firmware is unconfirmed; 8-byte frames fit our messages. CAN FD is a stretch goal that does not change `core/`.

## ADR-005: Real IMUs on a servo motion platform driven by a simulator
**Why:** Gives real sensor noise and latency in the loop (strong hardware-in-the-loop story) while keeping vehicle physics repeatable. **Cost:** servo bandwidth limits platform rates, so the simulated vehicle is time-scaled. **Alternative:** pure PC-injected sensor data (easier, weaker as a portfolio piece). Keep the injection mode as well, since CI needs it.

## ADR-006: Deterministic identical replicas with an estimator-state digest
**Why:** Bit-identical replicas make exact cross-checking possible and make silent divergence detectable. **Limit:** no protection against a shared software bug (see limitations).

## ADR-007: A damaged or lost frame consumes a sequence number
> **Superseded in mechanism by ADR-018** (frames carry SYNC's frame number and the receiver keeps a 32-cycle arrival history instead of a contiguous-counter tracker). The *requirement* it set still holds and is tested the same way: one lost, damaged or late frame costs exactly one sample, two isolated ones never isolate a healthy node.
**Decision:** `tfc::SeqTracker` advances its expected sequence number when a frame arrives with a bad CRC (`note_damaged`) and when a slot passes with nothing at all (`note_missing`). One corrupted or lost frame therefore costs one bad sample.
**Why:** Found with the virtual peers. Without this a single corrupted frame was followed by a false "sequence gap" on the next good frame, and a single lost frame likewise: two bad samples per event, so two isolated events inside the 3-of-5 window latched a healthy node, contradicting TFC-FDIR-004. The first half (corrupt) was fixed in PR #5; the audit before PR 1 showed the lost-frame half still cost two (two lost frames three apart latched a healthy node).
**Assumption:** the sender's counter advances with the schedule whether or not the frame reaches us. True for bus loss and for a node that hangs and recovers with its counter running (tested); a node that restarts its counter is reported once, which is the right outcome.
**Late frames (added after PR #8 merged, found by CI):** `note_missing()` alone broke the common jitter case. A peer frame that misses the 7 ms vote is marked missing and the expectation advances; the frame then arrives in the *next* frame carrying the number we had just skipped, which looked like a repeat, so a late frame cost two bad samples again. It showed up as `seq=2` on a healthy live run on the shared CI runner. The tracker now remembers how many slots it merely *assumed* missing (`pending_`, capped at 32) and accepts a frame carrying one of those numbers once, without moving the expectation. A burst is covered too: a stalled sender flushing several late frames at once (reproduced under CPU contention: `seq=2`; six repeats after the generalisation: `seq=0` with up to 8 `missing`). A genuine repeat, a number older than the assumed ones, or a frame after a damaged one is still an error. Regression tests were written first and failed before the fix.
**Alternatives:** weight sequence errors less than other bad samples (hides real sequence faults); drop sequence checking (loses the cheapest duplicate/replay detection). **Revisit:** if a sender is ever allowed to skip transmissions without advancing its counter, or if real hardware shows reordering (the late-arrival rule assumes a sender's frames stay in order).

## ADR-008: Duplex disagreement: attribute by continuity, otherwise hold the last good value and request Safe (sticky)
**Decision:** With two voting nodes that disagree, `RedundancyManager` (1) blames a node only if it jumped more than `duplex_arbitration_factor` (2.0) x tolerance from the last agreed value, set by the *previous* frame, while the other stayed within one tolerance; the output follows the consistent node. (2) Otherwise nobody is blamed, the output holds the last good value, and if unresolved disagreements persist (3 of the last 5 frames) a Safe request is raised that stays raised until `clear_safe_request()`. (3) Whenever any vote cannot produce a trustworthy value (unresolved duplex, no majority, no data) the output holds the last good value (`FrameReport::output`, `held_mask`).
**Why:** The audit found that in Duplex three single spikes inside five frames latched *both* survivors and dropped the system to Safe, while the same spikes in Triplex isolated only the culprit; and `vote3` returned `0.0` on a duplex miscompare with nothing holding the last command (FDIR-008 was only partly met). A step fault or a spike is easy to attribute: one node left the last agreed value, the other did not. A slow drift or a step barely above tolerance is not (both nodes are within reach of the reference), and a digest mismatch has no continuity at all: those must not be guessed, so they hold and request Safe, which is what FDIR-008 says.
**Research:** safety-critical systems keep the human or ground in the loop for anything the system cannot attribute. The Space Shuttle's computers voted a failed unit out and did not readmit it automatically; in the ALT-1 flight the crew manually isolated the failed computer and the vehicle landed on the remaining three (NASA write-up, klabs.org). Hence the sticky request that only an operator command lifts.
**Bug found while implementing, and the rule it produced:** the first version let the held (frozen) reference keep arbitrating. A replay with a 1.5 dps step on one survivor showed Safe requested at frame 202 and then the **healthy** node blamed at frame 229, because the vehicle had moved away from the stale value and the faulty node happened to sit near it. Arbitration now requires a *fresh* reference (previous frame trusted); a stale one never blames anyone. Cost: after an unresolved disagreement the system stays Safe even if one node later looks clearly wrong. That is the conservative outcome and is covered by tests.
**Alternatives rejected:** blame both (old behaviour: a transient in Duplex ends the mission); latest value wins / average (silently averages a faulty value, FDIR-008 forbids it); pick the node closest to the previous output with no margin (misattributes whenever the vehicle moves faster than the margin; the margins above are config and must be tuned per channel against real dynamics). **Revisit:** analytical redundancy (cross-sensor plausibility) could resolve drifts; that is later work.
**Amended by ADR-017 (and again for E19, below):** the reference the nodes are compared with is the last agreed value *carried forward by the last agreed step*, not the bare last value. Comparing with a standstill blamed the healthy node whenever the signal moved more than two tolerances per frame (the command channels), which the fault campaign found.

## ADR-009: Out-of-schedule traffic is counted by a catch-all filter and raises a rate alarm, not a latch
**Decision:** FC-A adds a catch-all CAN receive filter (second queue) whose frames are offered to the manager; frames on IDs outside the schedule are counted, and `bus_alarm_per_frame` (3) or more in one 10 ms frame raises `FrameReport::bus_alarm` for as long as it continues. FC-A prints `BUS ALARM RAISED/cleared`. No node is latched for it.
**Why:** The audit found babbling completely invisible in the live firmware: 2,352 stray frames on the bus and not a counter or alarm, because the acceptance filters (correctly, for the schedule slots) dropped them before the manager's `out_of_schedule` counter could see them, so TFC-FDIR-009's detector existed only in the replay tool. CAN frames carry an ID, not a sender, so a flood on unscheduled IDs cannot be attributed to a node; attributing it would be a guess. The response that is both honest and useful is the alarm (and, in the real system, the actuator node ignoring those IDs).
**Cost / revisit:** a catch-all filter makes every frame an interrupt on the target. At bring-up evaluate the cheaper hardware route (strict acceptance filters plus the FDCAN controller's lost-message and protocol-status counters, bus-load measurement on the logic analyzer). The real harm of a babbler (arbitration starvation) is a timing effect only hardware shows (F11, TFC-FDIR-009 stays an M requirement).

## ADR-010: Node life cycle: dwell, shadow-vote probation, strikes, and disabling
**Decision:** A node is in one of four states: `Healthy` (voting), `Latched` (excluded), `Probation` (excluded, being compared) or `Disabled` (excluded for the run). Latching counts a strike. A latched node first serves a **minimum dwell** (200 frames, 2 s). It then goes on **probation** when asked: by an operator command (policy `Manual`, the default), or automatically (policy `AutoTransient`, opt-in) only for a first latch whose cause looks transient (missing/damaged frames or a vote episode), never for a stuck sensor or digest mismatch and never for a repeat offender. On probation the node is still out of the vote, but every frame its data is compared with the **voted output of the healthy nodes** on all 8 channels and with their digest (a *shadow vote*). It must agree for 100 consecutive frames (300 after a repeat latch) to be readmitted; one bad or disagreeing frame sends it back to `Latched` (dwell restarts, new request needed, no new strike: it was never readmitted). **One node is on probation at a time.** A frame with no trustworthy reference (nobody healthy, Safe requested, the healthy nodes disagree) neither counts nor fails. **Strikes:** the 3rd latch of a node disables it (`max_strikes`); the 2nd when the cause is physical (`physical_causes`, default a stuck sensor or an intermittent fault, ADR-013). Strikes are counted over the whole run by default (`strike_window_frames` = 0), because a flight is minutes long. A `Disabled` node refuses reintegration; only the maintenance command `ClearDisabled` returns it to `Latched` with its strikes cleared. Safe stays sticky (ADR-008).
**Why (measured before this change):** the old `request_reintegration()` counted 100 *clean frames*, but a latched node was never compared with the vote, so "clean" only meant its frames arrived intact. A node still biased by 3 dps was readmitted at frame 120 (mode jumped back to Triplex), re-latched at 123, readmitted again at 230 and finally made permanent at 233. In Triplex the median hides that, but in Duplex a still-faulty node pulled next to a good one forces an unattributable disagreement (ADR-008). Now the same node is refused on its first probation frame (frame 213 in the test), and the report names the reason.
**Research (what each source supports; how I read it):**
- *Space Shuttle:* a computer that failed to meet a sync point was voted out and was not readmitted automatically; in the ALT-1 flight the crew manually isolated the failed computer (switch to STANDBY, then HALT) and the vehicle landed on the remaining three (NASA write-up on klabs.org, read directly). Hence Manual by default. The rule that a computer receiving two or more failure votes flags itself and resets its own votes comes from a search summary of the Sklaroff redundancy-management paper (a scan I could not read); it is not implemented here (listed under open items).
- *Boeing signal selection (patent US 5,710,776, via a summarising reader, not verbatim):* faults latch; failed signals keep being monitored so a latch can clear if the signal recovers; the number of latch clears is limited. This is the shape of probation (keep watching the excluded node) plus bounded strikes.
- *TTP/C (search summary of the Kopetz chapter):* exclusion and reintegration are separate mechanisms; a failed node stays failed for at least two TDMA rounds; at most one node is reintegrated per round. We mirror these as the minimum dwell and one-probation-at-a-time.
- *alpha-count (Bondavalli et al., IEEE Trans. Computers 2000; search summaries):* a count-and-threshold mechanism (+1 per error, x K per good observation) separates transient from intermittent and permanent faults. Strikes are the coarse version; the alpha-count itself is the planned next step for intermittent faults the 3-of-5 window cannot see.
- *AUTOSAR DEM (search summary of the spec):* counter-based debouncing before a fault is confirmed and "healing/aging" counted in operation cycles before it is cleared. Probation is a healing counter.
- *SpaceX:* nothing public about reintegration. The public description (three computers, each a pair of processors that cross-check; a disagreeing pair does not send commands) is a different layer: a node that fails silent.
**Differences from the plan I gave first, and why:** (1) strikes counted over the whole run, not "3 within 30 s": a flight is minutes long, the window is still configurable; (2) the strike limit for physical causes is 2, as proposed. **A requirement mismatch found on the way:** TFC-FDIR-007 said a channel that latches *twice* becomes permanent while the code defaulted to three; the requirement now states the policy exactly (3, or 2 for physical causes).
**Amended (fast reintegration, E6/D):** the dwell is 50 frames (0.5 s) after a *first, transient-looking* latch (cause only missing/CRC/sequence/vote) and stays 200 frames for a digest mismatch, a stuck or intermittent node and every repeat latch. Reason: every frame a node is out is a frame the system runs with less redundancy (and in Duplex a second fault can only end in Safe, E6), while the node must still pass the full 100-frame probation, and the strike limits still stop a node that keeps failing. `min_dwell_frames_transient` in the configuration; the full-dwell mechanism is still tested with it set to 200.
**Alternatives rejected:** readmitting after N clean frames without the shadow comparison (the bug above); readmitting without a dwell (a node faulting every few seconds would cycle in and out of the vote); automatic readmission as the default (airliners and the Shuttle keep a human in the loop, and an automatic policy can mask a wearing-out part); making the physical-cause rule a special case in the voter (it belongs to the supervisor).
**Known limits / open items:** each flight computer decides alone, with no agreement on membership, so two computers can hold different views of a node (the digest and a heartbeat state exchange are the planned remedy); a node that finds *itself* voted out keeps judging (the Shuttle rule above); recovery from "all nodes out" had no reference and needed a restart (fixed: ADR-014); the timing constants (200/100/300 frames) are proposals to be tuned from hardware measurements.

## ADR-011: Operator actions are CAN "ground command" frames
> **Amended by ADR-019:** the 4 reserved bytes now carry an authentication tag, `seq` is a command counter with a replay window, dangerous operations need an ARM frame first, and `disable` has an interlock. The sentences below describe the original design; what changed and why is in ADR-019.
**Decision:** Frame ID `0x510`, payload `opcode | node | 4 reserved | seq | CRC-8`. Opcodes: `Reintegrate`, `Disable`, `ClearDisabled`, `ClearSafe`. The manager applies commands at the end of the frame in which they arrive and reports each outcome (`accepted`, `already done`, or `refused: <why>`) in `FrameReport::commands`; FC-A prints it. All operations are idempotent, so a repeated frame is harmless and there is no replay protection. Scripts (`--command FRAME:OP[:NODE]`) and `tfc_peers command` send the same frames.
**Why:** a frame can be scripted at an exact frame number, so the whole life cycle (fault, latch, command, probation, readmission) is a single reproducible command line, offline through `tfc_replay` and live against FC-A; every flight computer on the bus receives the same command at the same time; and it works unchanged over the USB-CAN adapter later. `0x510` has lower priority than every control frame, as an operator action should. **Rejected:** a Zephyr shell on the console (only reachable by typing into one process, not scriptable to a frame number, a different path on `native_sim` and hardware).
**Limits:** no authentication; any node on the bus could send one. That is acceptable for a bench rig and would not be for a flight uplink.

## ADR-012: New fault kinds (`reboot`, `late`, `intermittent`) and a vote deadline in the replay
**Decision:** `reboot` (silent for `down` frames, then back with its sequence counter restarted at 0) and `late` (frames leave `us` microseconds late) are new fault kinds; every fault accepts `period`/`duty` to be intermittent. `tfc_replay` groups frames the way FC-A drains them: everything received between one 7 ms vote and the next (`--vote-us`, default 7000), not by 10 ms wall-clock buckets.
**Why:** reintegration needs a node that really comes back (`reboot`, with the restarted counter a real reboot produces); the timing family needs a fault that makes data stale rather than absent (`late`: a command leaving at 9.3 ms misses the 7 ms vote and is judged a frame late, with a stale digest); and intermittent faults are exactly what a 3-of-5 window cannot see (characterised in the tests; ADR for the alpha-count follows). Without the vote deadline the replay would call a frame that FC-A would reject "on time".
**Effect on existing results:** scheduled frames all leave before 7 ms, so no latch frame moves. Babble frames (8.0 ms) now land in the following frame: the replay raises the bus alarm one frame later than the live firmware, which sees them as they arrive.

## ADR-013: A leaky alpha-count catches intermittent faults the 3-of-5 window cannot see
**Decision:** Every node also feeds a leaky score (`AlphaCount`): +1 per bad frame, x 0.9 per good frame, latch at 3.0, OR'd with the existing 3-of-5 window. A latch the window did not cause carries the reason `intermittent fault`. That reason is in the *physical* class (`physical_causes`), so a repeat disables the node at the second strike, and it is never readmitted by the automatic policy. Fixed-point (Q16) arithmetic. `alpha_threshold = 0` switches it off.
**Why (measured, ADR-010 audit):** a node corrupting 20-40% of its frames for a whole run was never isolated: 3-of-5 needs three bad frames inside five, and a node that is bad one frame in three or two in five never gives it that. The vote masks each bad frame so the *output* stayed right, but the node was plainly sick and one more fault on another node would have been unmaskable. Real faults of this kind are common (loose connectors, marginal parts, EMI), which is why the fault-handling literature separates transient from intermittent from permanent.
**Research:** the α-count of Bondavalli, Chiaradonna, Di Giandomenico and Grandoni (IEEE Trans. Computers, 2000; read through search summaries of the abstract, not the full paper): +1 per error, multiplied by K (0 <= K <= 1) per success, threshold αT, diagnosing an intermittent or permanent fault; two thresholds improve it (not implemented: strikes and probation already give a second stage). AUTOSAR DEM's debouncing counters are the same family.
**Parameters, chosen by simulation (K, T) against fault patterns, then confirmed in the manager:**

| Pattern (bad frames) | 3-of-5 alone | alpha K=0.9, T=3 | measured in the replay (fault at 100) |
|---|---|---|---|
| single glitch, two-frame burst | never | never | never |
| 1 in 20, 1 in 10, 1 in 5 | never | never | never (no false isolation) |
| 3-frame burst (a hard fault) | on the 3rd frame | on the 3rd frame | unchanged: the window gets there first |
| 1 in 3 (33%) | never | 12 frames after start | frame 112 |
| 2 in 5 (40%) | never | 6 frames after start | frame 106 |
| 2 in 10 (20%, paired) | never | 21 frames after start | frame 121 |

Other settings tried: K=0.9/T=4 misses 1-in-5 and 2-in-10; K=0.95/T=4 catches 1-in-5 only after 40 frames and 2-in-10 after 31; K=0.8/T=3 misses 1-in-3. K=0.9, T=3 was chosen as a judgement call from this table: a node that is bad one frame in five or less (20%) is left alone, while one in three (33%) and two in five (40%) are isolated within about a dozen frames. A more patient setting (K=0.95, T=4) would also catch one in five, after 40 frames, at the price of a slower response elsewhere; where that line belongs depends on real error rates and is a tuning question for the rig. A long-run guard test (a glitch every 23 frames for 5,000 frames) proves a healthy node is never latched.
**Why OR with the window, and Q16:** the window is exact and fast for bursts and already specified (FDIR-004); the leaky count only adds what it cannot see, so hard-fault timing is unchanged (tested). Fixed-point because every replica must reach the same verdict from the same frames and float rounding is a needless way to disagree.
**Why an intermittent latch is "physical":** it recurs by definition; readmitting it once is reasonable (strike 1) but a second latch of the same kind means failing hardware, so the node is disabled instead of cycling through probation again and again.
**Limits:** the constants are tuned on a simulation of frame-level faults; real error rates will differ and must be re-tuned from measurements on the rig (the bench checks and the fault campaign). It judges frame-level badness only (missing, CRC, sequence, vote, digest, stuck); it does not look at sensor-noise statistics. No second threshold yet.


## ADR-014: Total loss is recoverable: probationers judge each other when nobody is healthy
**Decision:** If no node is `Healthy`, the nodes on probation use the vote *among themselves* as the reference instead of the (non-existent) voted output of the healthy nodes: each frame their data are voted (median, tolerance as usual); a node that is the odd one out, on a channel or in its digest, fails the probation; two that cannot be told apart (a duplex miscompare, three different values) make the frame neutral, so it neither counts nor fails. The "one probation at a time" rule is lifted *in that state only*. A node is still put on probation only by an operator request after its dwell, and still needs 100 (300 after a repeat) agreeing frames; one such cohort needs **at least two** members. As soon as one member is readmitted it is Healthy and the others continue against the ordinary shadow vote.
**Why (found by the fault campaign, group `total_loss`):** every node latched at once (a three-frame outage that hits all of them, or the last healthy node failing after the others were already out) was **unrecoverable**: probation compares a node with the voted output of the healthy nodes, there were none, so every frame was neutral for ever and the operator's commands changed nothing. ADR-010 had listed this as a known limit ("needs a restart"); the campaign showed how small the trigger is (3 frames) and that the restart is the *only* way out, i.e. one bus glitch ends the flight's redundancy for good. On the real system FC-A's own frames do not cross the bus, so the trigger there is "FC-A's own data are bad while B and C are out", rarer but not impossible.
**Why this design:** the alternatives were a *reset* command (needs a new operation, loses strikes and history, and an operator can already do it by power-cycling), an *automatic* restart when everything is latched (a decision to trust data that nobody has checked), or readmitting a lone survivor (it has nothing to be checked against). Mutual agreement of two or more candidates is the weakest assumption that still verifies something, and it is the same assumption the Triplex/Duplex vote already makes.
**Limits:** two nodes that fail the *same way* agree with each other (common-cause; no vote can help, see ADR-006 and the correlated-fault results); one candidate alone cannot be judged and waits; while Safe is requested (sticky) every frame has `held` outputs and is neutral, so the operator must clear Safe first.
**Tests:** `total_loss_*` (six C++ tests), `test_F46_*` (replay), campaign group `total_loss`, and four mutants (`cohort_*`).

## ADR-015: The manager protects its own state and configuration
**Decision:** (1) `RedundancyConfig` is validated and *sanitised* at construction: every invalid field (a tolerance that is not a finite positive number, M-of-N outside 1 <= M <= N <= 32, a stuck limit under 2, leaky-count constants out of range, an arbitration factor between 0 and 1, probation or strike limits that contradict each other) is replaced by its default, and the manager reports which (`config_errors()`, a `CONFIG ERROR` line on the console). (2) Node states and the Safe flag are stored with their bitwise complement (`GuardedByte`); the configuration is stored twice with a checksum over its field values. (3) At the start of every frame a *scrub* checks them: a node state that fails is set to `Latched` (excluded, recoverable by command), a Safe flag that fails is set to *requested*, a configuration that fails is restored from its second copy (or the defaults) **and Safe is requested**, an impossible command-queue length is clamped. Each repair is counted (`integrity_faults`), reported in the frame (`integrity_mask`) and printed. (4) Out-of-range node indices and operations are refused, never indexed.
**Why:** a redundancy manager is the one component whose wrong belief is not outvoted by anything, and the RAM of a flight computer is exposed to single-event upsets (NASA-STD-8719.13 and NPR 7150.2 expect safety-critical state to be protected and checked, with a fail-safe response). The campaign's fault model stops at the bus; this is the matching defence for the manager itself. Configuration is data from outside the proven code: a zero or NaN tolerance does not fail loudly, it makes every comparison false so the voter silently stops seeing disagreement (a mutant that skips this validation is killed by the tests).
**Why complement-and-compare, not a CRC or triple storage:** one flipped bit is the dominant upset and is detected exactly by a complement; triple storage with voting could *correct* it but triples the state and adds a vote that itself needs protecting; the fail-safe repair (exclude, Safe) costs little because the operator can restore a node with `reintegrate`. A detected upset is not trusted either way. Two flips that cancel are not detected; a periodic scrub of every frame is what keeps that window short.
**Fail-safe direction chosen per item:** node state -> `Latched` (excluded), not `Healthy` (trusted) and not `Disabled` (a permanent loss for one flipped bit); Safe flag -> requested; configuration -> restored, and Safe requested because the previous frame may have been judged with a wrong limit.
**Tests:** `seu_*`, `config_*` (C++); mutants `scrub_ignores_*`, `config_not_*`, `tolerance_not_validated`, `persistence_not_validated`, `queue_length_unchecked`. **Limits:** the monitors' own internal fields (window history, leaky score, sequence trackers) are not individually guarded; an upset there causes at worst one wrong frame verdict, which the persistence logic already tolerates. Protecting the *code* (flash ECC, program-counter watchdogs) is a hardware matter.

## ADR-016: A fault campaign with safety properties, and mutation testing to prove it can fail
**Decision:** Fault coverage is demonstrated by a *campaign* (`sim/campaign`): scenario grids (every fault kind x the parameter values around each threshold x all target nodes x start frames x Triplex/Duplex/Simplex contexts x seeds, plus recovery sequences, operator commands, two-fault and cascading cases, ten-minute runs) executed through the real core, with *oracles* checked on the per-frame decisions: properties that must **always** hold (M1-M8: mode follows the healthy count, only legal state transitions, a latched node never votes, Safe is sticky, outputs finite, a held output repeats exactly, one probation at a time except in total loss), properties that hold when **one** node is faulty (S1-S4: a healthy node is never isolated, the output stays within one tolerance of the truth, no Safe request in Triplex, no readmission while the fault is active), and advisory expectations derived from each fault's parameters (isolated, ignored, "gray" near a threshold). The campaign's own correctness is established by *mutation testing*: 49 deliberate bugs are injected into a copy of the core and each must be caught, by the C++ tests (`tools/mutation/run_unit.py`) and by the campaign (`campaign.mutate`).
**Why:** a list of hand-picked fault scenarios proves that those scenarios work. The user asked for every fault with many inputs and for irregularities to be found; properties checked over thousands of generated cases find the cases nobody thought of, and the first run did: a total-loss deadlock, a frozen command that got the healthy node isolated, a three-way digest split that latched every node. Mutation testing answers "would this test notice if the code were wrong?": the first version of the campaign missed 4 of 12 mutants (a hold that returned zero, a probation that could not fail, a strike limit that never disabled, a second simultaneous probation), which is how the M7/M8 oracles and the `commands_strikes` group came to exist.
**Phase sweeps:** a fault's effect can depend on *when* it starts (the vehicle's motion is sinusoidal, so what a frozen value looks like depends on the slope at that instant). The group `phase_sweep` starts every one of the 32 fault kinds at 40 different instants in Triplex and in Duplex. The defect in ADR-017 hid from the first campaign because `cmdstuck` had been tried at one start frame only, where the slope was gentle.
**Determinism as a regression oracle:** every scenario is exactly reproducible from its seed, and the results carry a hash of every per-frame decision. A refactor is proven behaviour-preserving by running the campaign before and after: across the split of `end_frame` into small steps, the new self-protection and the configuration validation, 8,033 of 8,049 shared scenarios had identical hashes, and the 16 that differed were exactly the scenarios of the two intended behaviour changes (12 total-loss recoveries and 4 `clear-disabled` dwell cases). The later change of ADR-017 altered 415 scenarios on purpose; each was reviewed (no property violated, five cases lost an isolation to a Safe request at a threshold magnitude).
**Limits:** the oracles judge frame-level behaviour on a synthetic motion profile and a synthetic estimator digest; timing is virtual; electrical and bus-arbitration effects need the rig. An expectation near a threshold is "gray" (reported, not judged) because noise decides which side it lands on.

## ADR-017: Duplex arbitration compares the nodes with where the signal should be, not where it was
**Decision:** `arbitrate()` judges the two surviving nodes against a *predicted* reference: the last agreed value plus the last agreed step (`2 x last - previous`), when two consecutive trusted frames exist; otherwise the bare last value as before. Blame still requires one node farther than `duplex_arbitration_factor` x tolerance from the reference while the other is within one tolerance; a stale reference (after a hold) still never blames anyone.
**Why (found by the fault campaign, group `phase_sweep`):** ADR-008 compared the nodes with the last agreed value. That works while the signal moves less than a tolerance per frame (the gyro and accel channels) but not on the command channels, where the tolerance is 0.01 deg and the command moves up to 0.05 deg per frame: a node that stopped following the motion (a *frozen command*, a stale or replayed frame) then sat exactly on the last agreed value and looked like the stable one, while the **healthy** node looked like the one that "jumped" more than 2 tolerances. In 63 of 80 start phases the healthy node was isolated, the faulty node became the only voter and **its frozen command became the output**, with no Safe request: a wrong actuator command from a single fault. `late`, `replay`, `cmdinvert`, `jitter` and `clockdrift` also put one wrong output through in Duplex before being attributed. In the other direction, `cmd_offset` in Duplex was *never* attributed (all 42 cases ended in Safe) because the healthy node's own motion exceeded one tolerance from the standstill reference. With the predicted reference the phase sweep has no violation of any property in any kind, and `cmd_offset` in Duplex is isolated in all 42 cases.
**Amended after the E19 measurement (see the end of this ADR):** the prediction is now used only where the signal really moves. **Cost and limits (of the first version):** the prediction adds the noise of two agreed samples (about 2.2 sigma for a gyro); at a fault magnitude exactly on the 2 x tolerance boundary the outcome (isolate or Safe) can flip with the noise, as it could before: of the cases that changed, five lost an isolation to a Safe request at those boundary magnitudes. Where the signal barely moves (the peaks of the sinusoid, slope under two tolerances per frame) neither node can be singled out and the system still holds and requests Safe, which is the fail-safe outcome. A commanded step is seen identically by both nodes, so it never reaches the arbitration. **Alternatives rejected:** a configured slew allowance per channel (needs the vehicle's dynamics, which the manager does not know and which differ per stage); a longer filter (more lag, more noise); trusting the node with the lower variance (a frozen node has zero variance).
**E19 amendment, measured:** sweeping the bias in Duplex over 60 seeds per magnitude showed that on the gyro channels (steps under half a tolerance per frame) the prediction only added noise: the isolate-or-Safe threshold moved from 2.0x tolerance (50% isolated) to about 2.3x and the transition widened from about 0.2x to 0.3x. The reference now adds the last agreed step with a weight that is 0 below one tolerance per frame, ramps to 1 at two tolerances per frame and stays 1 above (`reference()` in `redundancy.hpp`). Gyro and accel channels therefore behave exactly as before ADR-017: the per-frame decision hashes of all 531 Duplex scenarios of the groups `bias_gyro`, `bias_accel`, `drift`, `noise`, `scale`, `saturate` and `stuck` are identical to those of the core from before ADR-017. The command channels keep the E16 fix. Tests `reference_*`, mutants `reference_always_predicts`, `reference_never_predicts`.
**Tests:** `duplex_a_frozen_command_*` (C++, three), `test_F50_*` (replay, every phase), the 2,560-scenario `phase_sweep` group, and mutants `arbitration_standstill_reference` and `arbitration_extrapolates_backwards`.


## ADR-018: Frames carry SYNC's frame number, and the receiver checks the phase
**Decision:** The 8-bit `seq` field of every sensor and command frame is the low byte of the number of the SYNC frame that opened the cycle the frame belongs to, not a counter the node keeps for itself. The receiver (`PhaseTracker`, one per node and stream) compares it with the number of the frame it is collecting and keeps a 32-cycle history of which numbers arrived and which cycles delivered anything at all: the current number is **on time** (once); an earlier number (up to 31 back) that was not seen before and whose own cycle came up **empty** is a **late** frame (it missed the vote: one lost sample, its data are stale and the vote and digest judge them as before); anything else is **bad**: a number from the future, too old, a repeat, or an earlier number although its cycle already delivered a frame (a stream that is permanently one number behind). Bad frames set the `sequence` reason and are counted in `seq_bad`. The manager keeps its own frame count (`frame_number()`, incremented by `end_frame()`), or takes it from `begin_frame(k)`; the firmware passes SYNC's number.
**Why (campaign edge case E11):** the old counter only counted frames, so a node whose frames left more than about 4.5 ms early (or a clock drifting early) delivered a perfectly contiguous stream one whole frame ahead of the others: no sequence error, no missing frame, and a data error under one tolerance on this motion. The receiver's acceptance window is a whole cycle wide for a frame that takes 0.1 ms on the wire, so *when* a frame was sent could not be seen at all. The number says which frame the data belong to; a stream that is out of phase by one or more whole frames is now isolated in 3 frames, whatever the cause (early, late, replayed, duplicated, frozen counter, wrong frame number after a missed SYNC).
**Effects on the system:** no change to the frame format, the schedule or the bus load (the same byte is filled differently); a node that reboots or joins late takes the number from SYNC and is in phase at once, so a restart is no longer a sequence break (the `reboot` fault comes back in phase; `resync=0` models a node that does not resync and restarts from 0, which is isolated); the logic of "lost frame, damaged frame, late burst" got simpler (no `note_missing`/`note_damaged` bookkeeping across frames: absolute numbers make a lost frame leave no trace on the next one). `seqgap` now means "the frame number is off by `gap` for as long as the fault is active", so a permanent offset is a node out of phase and a windowed one is a one-frame glitch that 3-of-5 tolerates.
**A side benefit, measured:** the number is judged per node, not by comparing nodes, so a frame-level timing or replay fault is attributable even in Duplex, where a value comparison cannot say who is wrong. In the campaign, `late` in Duplex went from 0 of 40 isolated (all ended in Safe) to 40 of 40 isolated, `replay` from 21 to 33 of 33, and `clockdrift` and `early` are detected in 1 to 3 frames.
**Requirements this puts on the firmware of nodes B and C (docs/DEFERRED.md):** each node takes the frame number from SYNC (not from its own counter), keeps counting if SYNC is lost (and the sync-master takeover must keep the number continuous), and stamps the number of the cycle the data were sampled in. ACT should apply the same check.
**Limits:** it checks the phase in whole frames. A frame that is up to about 4.5 ms early (or 5.5 ms late for a gyro frame) still arrives in the right window with the right number and is accepted: seeing that needs the arrival time against the slot, which needs receive timestamps on the target (E11 option B, deferred, telemetry first). A frame at frame 0 that is numbered one behind cannot be told from a late frame of a cycle that never existed (nothing to contradict it). A 1-byte number wraps every 2.56 s, which is far longer than the 32-cycle history.
**Alternatives rejected:** keep the counter and add a per-node phase offset estimate (a learned offset is a state that can itself be wrong, and it hides a node that was never in phase); a 32-bit number (needs the 4 spare bytes of the frame, which are the data; the byte is enough for an equality check); timestamps in the payload (the sender's clock is exactly the thing being checked).
**Tests:** `phase_*` (C++, protocol), `frame_number_*`, `test_F43_*`, `test_a_node_whose_frame_number_stays_wrong_*`, the campaign groups `seqgap`, `early`, `reboot`, and mutants `phase_*`.

## ADR-019: Ground commands are authenticated, replay-protected and two-step; disabling has an interlock
**Decision (campaign edge case E10):** (1) **Tag.** Bytes 2-5 of the ground frame carry the low 32 bits of SipHash-2-4 over (frame id, opcode byte, node, counter) with a shared 128-bit key (`auth.hpp`; test vectors of the SipHash paper pass in C++ and in Python). A frame whose tag does not verify is dropped without a trace on the bus and counted in `commands_unauthentic`. (2) **Counter.** The counter byte must be 1 to `command_window` (32) ahead of the last accepted one (modulo 256); a repeat or an older one is a replay (`commands_replayed`); commands lost on the way are tolerated up to the window. (3) **ARM/EXECUTE.** Setting bit 7 of the opcode makes the frame an ARM for that operation and node; the matching EXECUTE must follow within `arm_window_frames` (250 = 2.5 s), and one ARM covers one EXECUTE. `clear-disabled` and `clear-safe` always need it, because both undo a protective action. (4) **Interlock tiers for `disable`:** of a node that is voting, with three healthy nodes (Triplex to Duplex) it is a plain command; with two (Duplex to Simplex) it needs an ARM; with one (the last voter) it needs an ARM and is reported loudly (`CRITICAL` on the console and in the report, counter `critical_commands`). Disabling a node that is not voting (latched, on probation) is plain. `reintegrate` never needs an ARM: the shadow vote is its check.
**Why:** the frame had a CRC and nothing else, so (a) a stale frame replayed by a stuck transmitter, a gateway or a recorded log could re-apply an old `disable` or lift a legitimate Safe request; (b) a corrupted frame that still passes CRC-8, or a node stuck on that id sending random payloads, passes a valid opcode and node with probability of about 7 in 10 million per frame (about one wrongly accepted command every few minutes at bus speed); (c) nothing stopped an operator, or a script, from disabling every node, one command at a time; (d) any node on the bus could issue a command. The tag closes (b) and (d) on the bench, the counter closes (a), the ARM closes the single-corrupted-frame class and gives (c) a deliberate second step, and the tiers keep (c) possible: in Duplex the manager cannot attribute a small fault (E6) and the way out is the operator isolating the node they know is bad, which a hard "never below two healthy nodes" refusal would have forbidden. This follows what flight programs do (hazardous commands are armed and then executed; the link is authenticated with sequence numbers; the internal bus is treated as a trusted segment).
**Rejected:** a hard refusal below two healthy nodes (blocks the E6 recovery); a MAC with a key per node (key management for a bench); AES-GCM (a hardware block this MCU may not have, no benefit for 5 bytes); counters kept in flash (the first accepted command after a reboot re-establishes the window, an acceptable gap).
**Key handling (bench):** the default key is the public SipHash test key `00..0f`, so the tools, the tests and the firmware agree out of the box. It protects nothing. The firmware takes `CONFIG_TFC_GROUND_KEY`, the host tools `$TFC_GROUND_KEY`; a configuration with authentication on and an all-zero key is replaced by the bench key and reported. Provisioning, storage and rotation of a real key are not designed (docs/DEFERRED.md).
**Self-protection:** the counter record and the ARM (code and timer) are guarded bytes, scrubbed every frame like the node states (ADR-015); a damaged counter record forgets the history (the next authentic command re-establishes it; fail-open on replay protection only, never on authenticity), a damaged ARM is cleared.
**Limits:** a 32-bit tag allows 2^32 guesses to forge; the comparison is not constant-time (irrelevant on a bench, relevant for a real uplink); a replay inside the window of a command *newer* than the last accepted one cannot exist by construction, but a recorded command whose counter is within the window and ahead of the last accepted one would be accepted (the usual limit of a counter window; a real uplink also needs freshness); there is no confidentiality. Authentication of the real uplink belongs at the vehicle's gateway (CCSDS-style link security), and all of this assumes the three flight computers see the same frames (inconsistent omission would leave their counters different; the window tolerates it, membership agreement would fix it).
**Tests:** `ground_*`, `arm_*`, `interlock_*` (C++), `siphash24_*`, `test_F52_*`, `test_F53_*`, the campaign group `ground_security` and `commands_*`, the fuzz operator (forged tags, stale counters, ARMed and un-ARMed commands), `seu_*` for the command state, and mutants `ground_*`, `arm_*`, `interlock_*`.

## ADR-020: Sensing: sensor health is separated from computer health (accepted); a ring re-homing of IMUs is a later stretch; no simultaneous multi-master IMU wiring
**Context:** each flight computer reads one IMU (SPI) and every one receives all three through the sensor exchange, so the three IMUs are already *logically* cross-strapped: any computer can use any IMU's sample. The owner's two requirements: **(1)** if an IMU breaks, its flight computer should not become useless; **(2)** if IMU A and flight computer B both break, flight computer A should be able to read IMU B. Today neither holds. For (1), the fault manager's unit of isolation is the node, so a bad gyro latches the whole computer (checked: `B:bias` on a gyro latches node B), although its command, computed from the consensus of all three samples, may be fine. For (2), IMU B's samples reach the bus only through computer B, so they vanish with it, and sensing falls to one IMU where physical access would leave two. The lecture's cross-strapped architecture (either box can reach either set of devices) costs more wiring, connectors and ways to fail.
**Decision, case 1 (accepted):** separate **sensor-channel health from compute-channel health** in the manager (TFC-ARCH-001). A gyro or accelerometer stream is a *sensor channel* (one per IMU); a command stream is a *compute channel* (one per computer). A bad sensor channel is excluded from the consensus, and its computer stays in the command vote for as long as its commands agree; only a disagreement of its *commands* removes it. Every computer sees the same samples, so all exclude the same channel in the same frame and the replicas stay identical (the digest still agrees). The number of healthy sensor channels and of healthy compute channels are reported separately and each has its own mode. No wiring changes, no parts. The sensor and command IDs keep their values (IMU k is hosted by computer k, so `0x100+k` is already "channel k"); what changes is their meaning in the manager.
**Decision, case 2 (deferred stretch, after S4): ring re-homing.** The backup host of IMU k is computer k-1 (IMU B to A, IMU C to B, IMU A to C), which covers the owner's example and its mirrors. Each computer gets a second SPI port for the IMU it backs up. One quad 2:1 bus switch per IMU (the 74CBTLV3257 class; availability, voltage and on-resistance to be checked) carries its four SPI signals (SCK, MOSI, MISO, CS) and connects it to **exactly one host at a time**, so SPI stays single-master and the consensus input stays identical for all computers. The select line defaults to home (pulled), so a dead supervisor changes nothing (SUP-007). Handover: the supervisor holds the dead computer in reset, then asserts one `ADOPT` line that both flips the switch and tells the backup host to read its second SPI port and publish the orphaned channel; the adopted channel starts on **probation** (a shadow vote against the consensus, as for a node in ADR-010) before it counts. It takes seconds (the supervisor has to declare the computer dead first), so it restores sensor redundancy after a double fault; it is not seamless fail-operational (TFC-ARCH-003).
**Decided now, because it is cheap now and expensive later (rule 10-11 of STAGED_BUILD):** (a) sensor frames identify the **channel**, not the sender, and at any time one publisher per channel (TFC-ARCH-009); (b) each IMU is powered from a rail that does not depend on its home computer being powered, otherwise it dies with it (TFC-ARCH-010: a small regulator per IMU from the node rail upstream of the relays, or a diode-OR of the home and backup hosts' 3.3 V; check the Adafruit board's logic level against the Nucleo's 3.3 V when choosing); (c) per-channel calibration constants are known to every computer (TFC-ARCH-011); (d) each node's harness reserves the second SPI pins (SPI1 on the Nucleo shares its clock pin with the LED, compatibility audit item 5: use other instances) and an `ADOPT` input.
**Why not simultaneous direct wiring (every computer reads every IMU at once):** (a) SPI has one master per slave; three masters need a switch or a multi-master I2C bus, where one stuck master hangs every IMU (a common cause across all three). (b) The sensor has, as far as the search of its documentation showed, no external sample trigger; computers reading the same IMU at different instants would get different samples, so the consensus inputs would differ, which breaks the bit-identical-replica assumption and the digest check (ARCHITECTURE section 4) unless the samples are exchanged over the bus anyway. (c) On a shared I2C bus nine reads at 400 kHz would not fit the 1.0 ms between the sample latch and the first sensor slot; on SPI the time is there but the wiring is not. (d) The lecture's own caution: more options, but more wiring, connectors and ways to fail. The ring above keeps one owner at a time instead.
**Alternatives:** *smart IMU nodes* (each IMU on its own small CAN node: sensing and computing become separate boxes and every computer receives the same frames by construction, so case 2 needs no switch; three more microcontrollers and CAN transceivers, about 72 USD at the parts-sheet prices for Nucleos, less with cheaper boards that are not priced here; the closest to real avionics, over budget); *a fourth, cold-spare IMU* (does not separate the failure modes); *the ring with a full 3x3 crosspoint* (any computer can adopt any IMU; many more switches for little gain).
**Consequences:** the manager's per-node state gets a second dimension, a real change to `core/`, the campaign oracles and the mutants. Case 1 can be written and tested in simulation now, because the virtual peers' gyro faults already leave the command stream untouched (F65); it becomes meaningful end to end with the estimator. Risks of case 2: the switch is a new element that can fail (default-home and the supervisor's logic bound it); an IMU that shorts its own SPI lines affects only its own bus until adopted; the supervisor's seconds-long handover. **Requirements:** TFC-ARCH-001 to 003, 009 to 011. **Tests:** F65, F73, F74.
**Order (owner, 4 Oct 2026):** the sensor and compute health split is done after the loop (P1) and before stage S3 (3 Nov), as its own change; the estimator is designed now to take channels with a valid flag so the split slots in. The degradation rule (what happens to a computer's command once its sensing is down to two channels) is decided by trade study TS-15 before the split is written.

## ADR-021 (accepted 4 Oct 2026: hold and ask): The third computer runs the previous known-good release; a disagreement between releases holds the output and asks for an operator
**Context:** three identical computers running identical software survive a hardware fault and not a software bug: a bug in the release makes all three wrong the same way, and the vote agrees on the wrong answer. Measured on the current voter: with B and C given the same `cmd_offset`, the healthy A is latched out at frame 102 and the system continues in Duplex on the two wrong nodes (F63). The Space Shuttle's answer was a fifth computer running separately developed software, used only if the whole primary set failed, monitoring the primary all along. Independent versions are not independent in practice (the Knight and Leveson experiment found independently written versions fail together more often than independence predicts), and an *older release of the same code* is weaker diversity still: it shares the specification, the algorithms and most of the code. What it does protect against is a **regression introduced since the known-good release**, which is the common case.
**Decision (proposed):** Nodes A and B run the current release; node C runs the **golden release**, a tagged release that passed the full campaign and the hardware stage tests, built reproducibly, changed only for safety fixes (TFC-ARCH-005). **A plain 2-of-3 vote cannot deliver the protection**: if the regression is common to A and B they agree, outvote the correct C, and the vote *isolates the healthy node*. So (TFC-ARCH-007): when two nodes of one release agree and the node of the other release disagrees beyond a **version tolerance** for M of N frames, **nobody is isolated, the output holds, and a Safe request is raised**; the operator resolves it by naming the node to trust (`disable` the other pair under an ARM, then `clear-safe`), exactly as for an unattributable Duplex disagreement (ADR-008). It does not pick a side because nothing in the data can say who is right.
**Needed for this to work:** (1) a frozen bus interface: a protocol version and the release's source hash in each heartbeat, and compatibility of the golden release with the current protocol (TFC-ARCH-004); (2) a digest over a version-stable, quantised state so the cross-check does not flag every release difference (TFC-ARCH-008; today the digest is over the whole estimator state and would mismatch by design); (3) a **behavioural-compatibility gate** in CI: replay the scenario set through both releases and require the commands to agree within the version tolerance, so a release that legitimately changes behaviour is noticed before it is fielded against the old golden (TFC-ARCH-006); (4) the mixed configuration in the test plan: three `native_sim` builds with different node numbers and releases on one `vcan0`, no hardware needed.
**Alternatives:** *vote only* (no protection against the case it is for); *golden as a monitor that takes over automatically when a plausibility envelope is exceeded by the pair* (the Shuttle model; more protection, but the envelope is a second model of the vehicle and a new thing that can be wrong; keep as a later option); *independent re-implementation of the estimator by a second author* (genuine diversity, a large effort, and a large project risk).
**Limits to state in the write-up:** protects against regressions, not against a bug present in both releases, a specification error, or an input-dependent bug (a warm spare shares those too: `MISSION_PHASES.md`). Diversity costs coverage: the golden release is a frozen build, so its own bugs are not fixed.
**Consequences:** the campaign's single-fault oracle S1 ("a healthy node is never isolated") is correct for single faults; the common-mode case is a *two-node* fault and needs its own scenario (F63). **Requirements:** TFC-ARCH-004 to 008. **Tests:** F63, F64; the campaign group `common_mode`.
**Status, 4 Oct 2026:** the owner chose **hold, request Safe, operator picks** (option b). Whether the old release should instead take over automatically (option c, the Shuttle model) is decided after the TS-3 data. Until then no automatic choice between releases exists in the manager: a disagreement beyond the version tolerance is frozen and the operator names the side to trust.

## ADR-022 (accepted 4 Oct 2026: the Lite build): A supervisor ("lizard brain") with its own clock and the watchdog the flight computers cannot give themselves
**Context:** the watchdogs listed in ARCHITECTURE section 5 live inside the software they protect, and the Mars rover's Sol 200 anomaly is the case where that is not enough: enough tasks stayed alive to keep servicing the watchdog while others were hung, and recovery was a hardware command from outside the flight software. The lecture's lizard brain is separate hardware that watches the computer, can swap or reset it, accepts hardware commands that bypass the flight software, and keeps its own copy of time.
**Decision (proposed):** add a supervisor node (`docs/SUPERVISOR.md`): its own processor family (RP2350), its own TCXO-based clock, powered upstream of every relay. It watches each node through two discrete lines (frame start and an end-of-frame kick sent only from the end of a *completed* frame), resets or power-cycles a node whose kicks stop, holds a looping node in reset, measures each node's frame clock against its own clock, sequences boot, and takes hardware commands over USB. It acts **only through discrete lines and USB, never through the flight bus**, never votes, and is **fail-passive**. The variant with a listen-only CAN tap (SUP-Full) is an upgrade that adds arrival-time margins and frame-number plausibility.
**Why it is not the time master:** a central time source would remove the sync-master takeover but make the supervisor a single point of failure for time. SYNC stays with the flight computers; the supervisor measures it.
**Alternatives:** *rely on the on-chip watchdogs* (the failure the deck's case study shows); *the supervisor as a bus guardian that gates each node's transmitter* (needs the transceiver's silent pin, which the CAN Pal breakout may not bring out; "hold in reset" does the same job for the cases we care about); *put the supervisor on the fault injector's Pico* (the injector exists to kill nodes and must not be the thing that protects them).
**Consequences:** one more part (Pico 2 and a clock module, about 6 USD plus the module; the relay channels already bought), nine lines to the nodes, a new firmware to write and test, and a new failure mode (a spurious reset), which is the safe direction. It subsumes the isolation line of TFC-FDIR-039 and the bus-alarm response of TFC-FDIR-040. **Requirements:** TFC-SUP-001 to 010, TFC-FDIR-038. **Tests:** F57, F58, F59, F66, F67, F68.
**Status, 4 Oct 2026:** the owner chose **SUP-Lite** (a second Pico 2 and a TCXO clock module, discrete lines only); SUP-Full stays an upgrade path. TS-0 recorded this. Consequence: TFC-SUP-005 (arrival margins from outside the computers) and the frame-number half of TFC-SUP-009 are Full-only and are not built; the arrival-time telemetry stays inside the computers (FDIR-037).

## ADR-023 (Safe mode accepted 4 Oct 2026; phases and the second ACT still proposed): The claim is fail-operational through sensing and computing, fail-passive beyond; mission phases set how many computers are hot; Safe is hold, then null
**Decision (proposed):** (1) **Scope of fail-operational:** after any one fault in a flight computer, an IMU, or a computer's link to the bus, the voted output continues within TFC-SYS-004 with no interruption of more than one frame (TFC-SYS-006). It is **not** claimed for the shared CAN bus, the actuator node, the servo power rail or the supervisor: those are fail-passive (hold, then null) and are listed as known limitations. A second ACT with a hardware output selector driven by the supervisor would extend the claim to the actuator node; it costs one Nucleo, one CAN Pal and a selector chip (about 24 USD plus the chip) and is a stretch decision (see `DEFERRED.md`). The servo, its rail and the platform are the plant, not the flight computer, and are outside the claim. (2) **Phases:** each node has a role (HOT, WARM, COLD) separate from its health, and a phase table fixes how many are hot in each phase (`docs/MISSION_PHASES.md`). Triplex is required in the phases that cannot be repeated; WARM is the existing shadow-vote probation entered by phase; promotion uses the probation criteria. (3) **Safe** is fail-passive: freeze at once, then null at a limited rate after `T_hold`, with ACT able to do it alone (`docs/SAFE_MODE.md`).
**Why:** it states plainly what the project does and does not tolerate, using the lecture's terms (fail-safe pulls over; fail-operational keeps driving because the spare was already turning), and each statement is testable.
**Alternatives:** claim full fail-operational (false while ACT is single); no phases (loses the warm-spare and promotion demonstration and the go/no-go gate); hold-forever Safe (no defined end).
**Requirements:** TFC-SYS-006, TFC-SAFE-001 to 007, TFC-PHASE-001 to 004.
**Status, 4 Oct 2026:** the open questions of `SAFE_MODE.md` and `FAULT_RESPONSE.md` were answered by the owner (null in ascent and depower on the pad; Safe does not end the simulated run; the 0.5 s hold is a parameter that TS-4 tunes; Simplex in ascent alerts only; ACT resumes from its stored output after a reset, to be confirmed by the servo no-signal measurement; the phase minimums stand; the supervisor never resets the last agreeing computer on its own). Phases (`MISSION_PHASES.md`) and the second ACT remain proposals.

## ADR-024 (accepted 4 Oct 2026): The servos are the platform; the simulator is a C++ library with a runner; the vehicle is a full 6-DOF ascent
**Context:** the documents disagreed about what the two servos do. The overview said the actuator node drives a servo; the architecture said they tilt the platform that carries the IMUs, driven by the Pico from the simulator. The parts sheet has exactly two servos, described as the platform's pitch and yaw axes, so only the second can be true.
**Decision (owner, 4 Oct 2026):** (1) **The servos are the platform**, driven by the Pico from the simulator's attitude. ACT has no PWM output: it votes the three commands and puts the voted gimbal command on the bus, and its Safe action is the value of that command. The platform has its own protection in the Pico (rate and travel limits, a watchdog on the PC link) and the E-stop. (2) **The simulator is a C++ library plus a small runner** that speaks SocketCAN and USB; Python is for scenario files and analysis. One vehicle model serves the tests, the campaign, the trade-study sweeps and the rig, so there is nothing to keep in step. (3) **The physics is a full 6-DOF ascent** (position, velocity, attitude, variable mass and inertia, thrust with altitude, TVC, atmosphere, wind, aerodynamic instability, engine-out), which the owner chose over the two-plane attitude model that had been recommended as sufficient. The platform can reproduce only two of the rotations (the long axis's tilt in the pitch and yaw planes, within about 45 degrees); roll is not reproduced, and the accelerometer on the platform reads gravity, not the vehicle's specific force, so the simulator also has a **vehicle-true sensor mode** for software-only runs.
**Why the 6-DOF choice is still worth stating plainly:** it costs about a week and the rig cannot show most of what it adds; its value is credibility (a real max-Q, a real gravity turn, a mass that changes by a factor of five) and a model whose plant changes through the flight, which forces gain scheduling, the thing a real controller needs. The risk is the schedule: if it slips, the fallback is the two-plane model already in `tools/vehicle`, behind the same interface.
**Consequences:** the Safe-mode and fault-response documents are corrected (this change); the vehicle simulator has its own design (`docs/VEHICLE_SIM.md`); the controller gets a gain schedule and the guidance table grows to 16 points; the protocol gains the simulator's frames (`0x501` to `0x504`) and ACT's output frame (`0x300`); the Pico firmware becomes a platform driver first and a fault injector second. **Requirements:** TFC-SIM-001 to 006, TFC-PLAT-001 to 004.
