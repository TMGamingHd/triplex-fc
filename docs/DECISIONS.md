# Design decisions (ADR log)

## ADR-001: C++17 subset for flight logic
**Decision:** Portable `core/` in C++17, header-only, no heap, no exceptions, no RTTI, warnings as errors.
**Why:** SpaceX's public Starship software postings ask for C++, Rust or another systems language and real-time embedded experience; public writing about its flight software describes C and C++. A restricted C++ subset is the industry pattern for flight code (MISRA/JSF-style rules). **Alternatives:** C (simpler to certify, less expressive), Rust (attractive, but a weaker toolchain fit for Zephyr today). **Revisit:** Rust for a non-critical tool.

## ADR-002: Zephyr RTOS on the target
**Decision:** Zephyr, with the portable core tested on `native_sim`.
**Why:** Modern, upstream, actively maintained, first-class support for the Nucleo-G474RE (FDCAN, SPI, PWM, watchdogs) and an ISM330DHCX sensor binding, plus real space-industry interest (for example NASA cFS being ported to Zephyr by a space-electronics company). Its `native_sim` target lets the same firmware run on a PC for CI. **Honest note:** SpaceX's own stack is not public and what has been described publicly is dated (Linux and VxWorks have been mentioned). No one will hire on RTOS brand; what transfers is deterministic scheduling, priority discipline, timing measurement and testing. **Alternatives:** FreeRTOS (ubiquitous, lighter), bare metal (max determinism, fewer marketable skills). **Fallback:** if Zephyr bring-up stalls beyond milestone M1 by 2 weeks, drop to FreeRTOS; `core/` is unaffected.

## ADR-003: Time-triggered schedule at 100 Hz
**Why:** Predictable, measurable, easy to reason about for voting, and it mirrors how safety-critical buses are scheduled. **Alternative:** event-driven; simpler but jitter is harder to bound.

## ADR-004: Classic CAN 1 Mbit/s for v1
**Why:** The USB-CAN adapter's FD support with default firmware is unconfirmed; 8-byte frames fit our messages. CAN FD is a stretch goal that does not change `core/`.

## ADR-005: Real IMUs on a servo motion platform driven by a simulator
**Why:** Gives real sensor noise and latency in the loop (strong hardware-in-the-loop story) while keeping vehicle physics repeatable. **Cost:** servo bandwidth limits platform rates, so the simulated vehicle is time-scaled. **Alternative:** pure PC-injected sensor data (easier, weaker as a portfolio piece). Keep the injection mode as well, since CI needs it.

## ADR-006: Deterministic identical replicas with an estimator-state digest
**Why:** Bit-identical replicas make exact cross-checking possible and make silent divergence detectable. **Limit:** no protection against a shared software bug (see limitations).

## ADR-007: A damaged or lost frame consumes a sequence number
**Decision:** `tfc::SeqTracker` advances its expected sequence number when a frame arrives with a bad CRC (`note_damaged`) and when a slot passes with nothing at all (`note_missing`). One corrupted or lost frame therefore costs one bad sample.
**Why:** Found with the virtual peers. Without this a single corrupted frame was followed by a false "sequence gap" on the next good frame, and a single lost frame likewise: two bad samples per event, so two isolated events inside the 3-of-5 window latched a healthy node, contradicting TFC-FDIR-004. The first half (corrupt) was fixed in PR #5; the audit before PR 1 showed the lost-frame half still cost two (two lost frames three apart latched a healthy node).
**Assumption:** the sender's counter advances with the schedule whether or not the frame reaches us. True for bus loss and for a node that hangs and recovers with its counter running (tested); a node that restarts its counter is reported once, which is the right outcome.
**Late frames (added after PR #8 merged, found by CI):** `note_missing()` alone broke the common jitter case. A peer frame that misses the 7 ms vote is marked missing and the expectation advances; the frame then arrives in the *next* frame carrying the number we had just skipped, which looked like a repeat, so a late frame cost two bad samples again. It showed up as `seq=2` on a healthy live run on the shared CI runner. The tracker now remembers how many slots it merely *assumed* missing (`pending_`, capped at 32) and accepts a frame carrying one of those numbers once, without moving the expectation. A burst is covered too: a stalled sender flushing several late frames at once (reproduced under CPU contention: `seq=2`; six repeats after the generalisation: `seq=0` with up to 8 `missing`). A genuine repeat, a number older than the assumed ones, or a frame after a damaged one is still an error. Regression tests were written first and failed before the fix.
**Alternatives:** weight sequence errors less than other bad samples (hides real sequence faults); drop sequence checking (loses the cheapest duplicate/replay detection). **Revisit:** if a sender is ever allowed to skip transmissions without advancing its counter, or if real hardware shows reordering (the late-arrival rule assumes a sender's frames stay in order).

## ADR-008: Duplex disagreement: attribute by continuity, otherwise hold the last good value and request Safe (sticky)
**Decision:** With two voting nodes that disagree, `RedundancyManager` (1) blames a node only if it jumped more than `duplex_arbitration_factor` (2.0) x tolerance from the last agreed value, set by the *previous* frame, while the other stayed within one tolerance; the output follows the consistent node. (2) Otherwise nobody is blamed, the output holds the last good value, and if unresolved disagreements persist (3 of the last 5 frames) a Safe request is raised that stays raised until `clear_safe_request()`. (3) Whenever any vote cannot produce a trustworthy value (unresolved duplex, no majority, no data) the output holds the last good value (`FrameReport::output`, `held_mask`).
**Why:** The audit found that in Duplex three single spikes inside five frames latched *both* survivors and dropped the system to Safe, while the same spikes in Triplex isolated only the culprit; and `vote3` returned `0.0` on a duplex miscompare with nothing holding the last command (FDIR-008 was only partly met). A step fault or a spike is easy to attribute: one node left the last agreed value, the other did not. A slow drift or a step barely above tolerance is not (both nodes are within reach of the reference), and a digest mismatch has no continuity at all: those must not be guessed, so they hold and request Safe, which is what FDIR-008 says.
**Research:** safety-critical systems keep the human or ground in the loop for anything the system cannot attribute. The Space Shuttle's computers voted a failed unit out and did not readmit it automatically; in the ALT-1 flight the crew manually isolated the failed computer and the vehicle landed on the remaining three (NASA write-up, klabs.org). Hence the sticky request that only an operator command lifts.
**Bug found while implementing, and the rule it produced:** the first version let the held (frozen) reference keep arbitrating. A replay with a 1.5 dps step on one survivor showed Safe requested at frame 202 and then the **healthy** node blamed at frame 229, because the vehicle had moved away from the stale value and the faulty node happened to sit near it. Arbitration now requires a *fresh* reference (previous frame trusted); a stale one never blames anyone. Cost: after an unresolved disagreement the system stays Safe even if one node later looks clearly wrong. That is the conservative outcome and is covered by tests.
**Alternatives rejected:** blame both (old behaviour: a transient in Duplex ends the mission); latest value wins / average (silently averages a faulty value, FDIR-008 forbids it); pick the node closest to the previous output with no margin (misattributes whenever the vehicle moves faster than the margin; the margins above are config and must be tuned per channel against real dynamics). **Revisit:** analytical redundancy (cross-sensor plausibility) could resolve drifts; that is later work.

## ADR-009: Out-of-schedule traffic is counted by a catch-all filter and raises a rate alarm, not a latch
**Decision:** FC-A adds a catch-all CAN receive filter (second queue) whose frames are offered to the manager; frames on IDs outside the schedule are counted, and `bus_alarm_per_frame` (3) or more in one 10 ms frame raises `FrameReport::bus_alarm` for as long as it continues. FC-A prints `BUS ALARM RAISED/cleared`. No node is latched for it.
**Why:** The audit found babbling completely invisible in the live firmware: 2,352 stray frames on the bus and not a counter or alarm, because the acceptance filters (correctly, for the schedule slots) dropped them before the manager's `out_of_schedule` counter could see them, so TFC-FDIR-009's detector existed only in the replay tool. CAN frames carry an ID, not a sender, so a flood on unscheduled IDs cannot be attributed to a node; attributing it would be a guess. The response that is both honest and useful is the alarm (and, in the real system, the actuator node ignoring those IDs).
**Cost / revisit:** a catch-all filter makes every frame an interrupt on the target. At bring-up evaluate the cheaper hardware route (strict acceptance filters plus the FDCAN controller's lost-message and protocol-status counters, bus-load measurement on the logic analyzer). The real harm of a babbler (arbitration starvation) is a timing effect only hardware shows (F11, TFC-FDIR-009 stays an M requirement).

## ADR-010: Node life cycle: dwell, shadow-vote probation, strikes, and disabling
**Decision:** A node is in one of four states: `Healthy` (voting), `Latched` (excluded), `Probation` (excluded, being compared) or `Disabled` (excluded for the run). Latching counts a strike. A latched node first serves a **minimum dwell** (200 frames, 2 s). It then goes on **probation** when asked: by an operator command (policy `Manual`, the default), or automatically (policy `AutoTransient`, opt-in) only for a first latch whose cause looks transient (missing/damaged frames or a vote episode), never for a stuck sensor or digest mismatch and never for a repeat offender. On probation the node is still out of the vote, but every frame its data is compared with the **voted output of the healthy nodes** on all 8 channels and with their digest (a *shadow vote*). It must agree for 100 consecutive frames (300 after a repeat latch) to be readmitted; one bad or disagreeing frame sends it back to `Latched` (dwell restarts, new request needed, no new strike: it was never readmitted). **One node is on probation at a time.** A frame with no trustworthy reference (nobody healthy, Safe requested, the healthy nodes disagree) neither counts nor fails. **Strikes:** the 3rd latch of a node disables it (`max_strikes`); the 2nd when the cause is physical (`physical_causes`, default a stuck sensor). Strikes are counted over the whole run by default (`strike_window_frames` = 0), because a flight is minutes long. A `Disabled` node refuses reintegration; only the maintenance command `ClearDisabled` returns it to `Latched` with its strikes cleared. Safe stays sticky (ADR-008).
**Why (measured before this change):** the old `request_reintegration()` counted 100 *clean frames*, but a latched node was never compared with the vote, so "clean" only meant its frames arrived intact. A node still biased by 3 dps was readmitted at frame 120 (mode jumped back to Triplex), re-latched at 123, readmitted again at 230 and finally made permanent at 233. In Triplex the median hides that, but in Duplex a still-faulty node pulled next to a good one forces an unattributable disagreement (ADR-008). Now the same node is refused on its first probation frame (frame 213 in the test), and the report names the reason.
**Research (what each source supports; how I read it):**
- *Space Shuttle:* a computer that failed to meet a sync point was voted out and was not readmitted automatically; in the ALT-1 flight the crew manually isolated the failed computer (switch to STANDBY, then HALT) and the vehicle landed on the remaining three (NASA write-up on klabs.org, read directly). Hence Manual by default. The rule that a computer receiving two or more failure votes flags itself and resets its own votes comes from a search summary of the Sklaroff redundancy-management paper (a scan I could not read); it is not implemented here (listed under open items).
- *Boeing signal selection (patent US 5,710,776, via a summarising reader, not verbatim):* faults latch; failed signals keep being monitored so a latch can clear if the signal recovers; the number of latch clears is limited. This is the shape of probation (keep watching the excluded node) plus bounded strikes.
- *TTP/C (search summary of the Kopetz chapter):* exclusion and reintegration are separate mechanisms; a failed node stays failed for at least two TDMA rounds; at most one node is reintegrated per round. We mirror these as the minimum dwell and one-probation-at-a-time.
- *alpha-count (Bondavalli et al., IEEE Trans. Computers 2000; search summaries):* a count-and-threshold mechanism (+1 per error, x K per good observation) separates transient from intermittent and permanent faults. Strikes are the coarse version; the alpha-count itself is the planned next step for intermittent faults the 3-of-5 window cannot see.
- *AUTOSAR DEM (search summary of the spec):* counter-based debouncing before a fault is confirmed and "healing/aging" counted in operation cycles before it is cleared. Probation is a healing counter.
- *SpaceX:* nothing public about reintegration. The public description (three computers, each a pair of processors that cross-check; a disagreeing pair does not send commands) is a different layer: a node that fails silent.
**Differences from the plan I gave first, and why:** (1) strikes counted over the whole run, not "3 within 30 s": a flight is minutes long, the window is still configurable; (2) the strike limit for physical causes is 2, as proposed. **A requirement mismatch found on the way:** TFC-FDIR-007 said a channel that latches *twice* becomes permanent while the code defaulted to three; the requirement now states the policy exactly (3, or 2 for physical causes).
**Alternatives rejected:** readmitting after N clean frames without the shadow comparison (the bug above); readmitting without a dwell (a node faulting every few seconds would cycle in and out of the vote); automatic readmission as the default (airliners and the Shuttle keep a human in the loop, and an automatic policy can mask a wearing-out part); making the physical-cause rule a special case in the voter (it belongs to the supervisor).
**Known limits / open items:** each flight computer decides alone, with no agreement on membership, so two computers can hold different views of a node (the digest and a heartbeat state exchange are the planned remedy); a node that finds *itself* voted out keeps judging (the Shuttle rule above); recovery from "all nodes out" has no reference and needs a restart; the timing constants (200/100/300 frames) are proposals to be tuned from hardware measurements.

## ADR-011: Operator actions are CAN "ground command" frames
**Decision:** Frame ID `0x510`, payload `opcode | node | 4 reserved | seq | CRC-8`. Opcodes: `Reintegrate`, `Disable`, `ClearDisabled`, `ClearSafe`. The manager applies commands at the end of the frame in which they arrive and reports each outcome (`accepted`, `already done`, or `refused: <why>`) in `FrameReport::commands`; FC-A prints it. All operations are idempotent, so a repeated frame is harmless and there is no replay protection. Scripts (`--command FRAME:OP[:NODE]`) and `tfc_peers command` send the same frames.
**Why:** a frame can be scripted at an exact frame number, so the whole life cycle (fault, latch, command, probation, readmission) is a single reproducible command line, offline through `tfc_replay` and live against FC-A; every flight computer on the bus receives the same command at the same time; and it works unchanged over the USB-CAN adapter later. `0x510` has lower priority than every control frame, as an operator action should. **Rejected:** a Zephyr shell on the console (only reachable by typing into one process, not scriptable to a frame number, a different path on `native_sim` and hardware).
**Limits:** no authentication; any node on the bus could send one. That is acceptable for a bench rig and would not be for a flight uplink.

## ADR-012: New fault kinds (`reboot`, `late`, `intermittent`) and a vote deadline in the replay
**Decision:** `reboot` (silent for `down` frames, then back with its sequence counter restarted at 0) and `late` (frames leave `us` microseconds late) are new fault kinds; every fault accepts `period`/`duty` to be intermittent. `tfc_replay` groups frames the way FC-A drains them: everything received between one 7 ms vote and the next (`--vote-us`, default 7000), not by 10 ms wall-clock buckets.
**Why:** reintegration needs a node that really comes back (`reboot`, with the restarted counter a real reboot produces); the timing family needs a fault that makes data stale rather than absent (`late`: a command leaving at 9.3 ms misses the 7 ms vote and is judged a frame late, with a stale digest); and intermittent faults are exactly what a 3-of-5 window cannot see (characterised in the tests; ADR for the alpha-count follows). Without the vote deadline the replay would call a frame that FC-A would reject "on time".
**Effect on existing results:** scheduled frames all leave before 7 ms, so no latch frame moves. Babble frames (8.0 ms) now land in the following frame: the replay raises the bus alarm one frame later than the live firmware, which sees them as they arrive.
