# Simulation and virtual peers

Two things live here:

| Part | Status |
|---|---|
| `tfc_peers/`: **virtual peers** (S1b): fake FC-A/B/C that put real, fault-injectable traffic on the flight bus | Done (host) |
| Vehicle simulator (6-DOF ascent, platform-rate limiter, SocketCAN gateway, fault-campaign runner) | Not started (milestone M3) |

## What the virtual peers are
Until the boards arrive (and later, to test failures that are dangerous or awkward to cause for real),
the PC plays the other flight computers. `tfc_peers` generates exactly the frames a real FC-B or FC-C
would send every 10 ms (gyro `0x100+n`, accel `0x110+n`, command `0x200+n`; CRC-8 and sequence number
included, slots as in `docs/ARCHITECTURE.md` section 3), with realistic sensor noise, and can break any
of them on purpose: fail-silent, stuck, bias, drift, spikes, saturation, corrupted frames, wrong
commands, digest divergence, babbling, sequence gaps (`python3 -m tfc_peers faults`). Each fault kind maps
to a row of `docs/FAULT_MATRIX.md`.

There are two ways to use the traffic:

1. **Offline** (`record`): write a `candump -L`-format log in virtual time (no sleeping, exactly
   repeatable) and replay it through the **real `core/` code** with `tfc_replay`, a host model of FC-A's
   consensus + FDIR step. This is what CI does. It answers "does `core/` make the right decision on the
   bytes a real peer would put on the wire?"
2. **Live** (`run`): send the traffic at 100 Hz onto a SocketCAN interface: `vcan0` (virtual, no
   hardware) now, the USB-CAN adapter (`can0`) when it arrives. FC-A, real or `native_sim`, then sees fake
   peers B and C.

Not covered: real bus timing, arbitration, bus-off and wiring faults (F11 timing, F12-F15, F17). Those need
the real nodes. Python send timing is **not real-time**; `run` prints its own lateness statistics so you can
see how good the fake peers' timing was, and it must never be quoted as a flight-computer measurement.

## Use it
Everything is pure standard-library Python 3.10+; nothing to install. Run from `sim/`:
```bash
cd sim
python3 -m tfc_peers faults                     # list fault kinds and options
python3 -m tfc_peers record --nodes A,B,C --frames 400 \
    --fault B:bias:start=100,mag=3 --out /tmp/bias.log      # 4 s of traffic, B develops a bias at frame 100
python3 -m tfc_peers decode /tmp/bias.log --limit 12        # human-readable
../build/host/tfc_replay /tmp/bias.log --verbose            # what would FC-A decide?
```
Fault syntax: `NODE:KIND[:key=value,...]`, repeatable. `start`/`end` are 10 ms frame numbers
(`end` exclusive). Examples: `B:dropout:start=100`, `C:stuck:start=50`, `A:bias:sensor=accel,axis=2,mag=0.2`,
`B:corrupt:start=100,end=101,p=1.0`, `B:babble:start=100,n=5`. Same `--seed` gives identical traffic.

`tfc_replay` prints `latch.B=102`, `mode=duplex`, frame-error counters, and can assert outcomes
(`--expect-latch B:102`, `--expect-latch B:100-102`, `--expect-no-latch B`, `--expect-mode duplex`,
`--expect-min crc_bad:3`); it exits 1 if an expectation fails.

### Live on a virtual CAN bus
```bash
./scripts/setup_vcan.sh            # once per boot; needs sudo (loads the vcan module, creates vcan0)
python3 -m tfc_peers listen --iface vcan0                     # terminal 1: decoded bus monitor
python3 -m tfc_peers run --iface vcan0 --nodes B,C --frames 500 \
    --fault B:dropout:start=300                               # terminal 2: 5 s, B dies after 3 s
```
Checked on `vcan0` (2026-09-30, desktop Ubuntu, Python 3.14): 500 frames with `B:dropout:start=300` delivered
2400 frames to the monitor (= 500 x 6 - 200 x 3), B's last frame had sequence 43 (= 299 mod 256), no CRC errors
or stray IDs; sender lateness p50 7 us, p99 45 us, max 100 us. Desktop Linux gives no latency guarantee, so
treat this as "good enough for logic tests", not as a bound.

`sudo apt install can-utils` adds `candump vcan0` / `canplayer` if you want the standard tools; the log
format is compatible with both.

## Tests
```bash
cmake -S .. -B ../build/host -G Ninja -DTFC_SANITIZE=ON && cmake --build ../build/host
python3 -m unittest discover -s tests -t .     # 53 tests: protocol, peers, faults, end-to-end through core/
```
`ctest --test-dir build/host` runs the same suite (`peers_e2e`). The end-to-end tests are skipped if
`tfc_replay` has not been built.

## How it stays honest
- `tfc_peers/protocol.py` mirrors `core/include/tfc/protocol.hpp`. Five golden frames generated by the C++
  code are pinned in `tests/test_protocol.py`, and the replay tool decodes every recorded frame with the C++
  decoder, so any drift between the two shows up as CRC errors, not as a silent mismatch.
- Expected detection times in `tests/test_replay.py` come from `docs/REQUIREMENTS.md` (FDIR-001..004, 011)
  and match the SIL scenarios in `tests/test_triplex_scenarios.cpp` (bias: fault frame + 2).
- Two things the peers cannot know yet: the real estimator-state **digest** (they use a synthetic function
  of the frame number, identical across healthy peers) and **SYNC/heartbeat/ACT payloads** (not defined in
  `protocol.hpp` yet). Digest checking against real FC-A needs the estimator from M3.
